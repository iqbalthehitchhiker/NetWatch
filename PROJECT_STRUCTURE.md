# NetWatch — Project Structure & Capabilities

## What is NetWatch?

NetWatch is an interactive **network monitoring and diagnostic trainer** for students learning how to read a live network operations dashboard and identify fault root causes from evidence — without configuring, building, or touching a real network.

The core learning loop is:

1. **Watch** — a scripted network incident unfolds second-by-second across six monitoring panels (telemetry charts, topology map, alert list, packet capture, device metrics, event log)
2. **Investigate** — observe which devices degrade, how links change colour, what packets appear, which alerts fire, and in what order
3. **Diagnose** — select the correct root cause from a multiple-choice set, grounded in the evidence on screen

Nothing is simulated in the abstract. Every number, colour, packet row, and alert line is generated by a deterministic tick engine reacting to a scripted incident. Students are taught to read what a real monitoring tool would actually show.

## What NetWatch Can Do

### Simulation Engine
- Runs a **tick-based simulation** (one tick per second) that lerp-eases device telemetry toward scripted incident targets with realistic noise
- Supports **three network topologies**: Branch Office (gateway + web + DB + workstations), AI Training Cluster (GPU nodes + scheduler + storage), Small Office LAN (gateway + web + switch + workstations)
- Ships **six scripted incidents**, each with 3–4 timed stages:
  - **DDoS at the Edge** — volumetric SYN flood overwhelming the gateway
  - **Runaway Database Query** — disk-I/O-bound query cascading to web server latency
  - **GPU Cluster Thermal Throttling** — sustained GPU load triggering thermal throttle on one node
  - **The Overload That Came From Inside** — internal host exhausting the gateway's connection-tracking table
  - **The Web Server That Forgot to Let Go** — application memory leak leading to swap-driven CPU spike
  - **Broadcast Storm on the LAN** — switching loop generating a broadcast storm that saturates SW-1
- Computes **per-device health status** (healthy / warning / degraded / critical / offline) against hard thresholds that differ by device type
- Generates a **live packet capture feed** with protocol-appropriate flagged rows matching each incident's signature (SYN flood, slow-query frames, connection churn, ARP/STP loop frames, etc.)
- Catches per-device tick exceptions and continues advancing all other devices — the simulation never halts on a single fault

### Six Monitoring Panels
| Panel | What it shows |
|---|---|
| **Overview** | Stat bar (6 live counters: healthy devices, active alerts, avg latency, avg CPU, packet loss, sim time) + rolling sparklines (traffic, CPU, latency, 30-tick window) + device health grid |
| **Topology** | SVG network diagram with nodes coloured by health (green/amber/red/grey) and links coloured by latency/loss thresholds. Non-colour text labels (WARN/DEGRADED/CRIT) for accessibility |
| **Devices** | Per-device inventory table with CPU bar, memory, and type-specific extras (GPU/VRAM for AI nodes, traffic for switches, disk/temp for servers) |
| **Alerts** | Timestamped alert list (CRITICAL / WARNING / INFO), newest first, with device label and plain-English detail text |
| **Packets** | Simulated packet capture table — timestamp, src IP, dst, protocol tag, byte length, and info field. Anomalous rows highlighted red. Filter buttons (All / Flagged / TCP / UDP / ICMP / DNS / ARP / STP) |
| **Metrics & Logs** | Per-link quality stats (avg latency, jitter, bandwidth utilization, most-loaded link, packet loss, retransmissions) + device telemetry snapshot + event log with timestamps |
| **History** | Longer-window (24-point) Traffic + CPU overlay chart for timeline analysis |

### History chart sits inside the History & Logs tab; the three sparklines sit in the Overview tab.

### Two Operating Modes
**Teach Mode** (no login, no scoring, no attempt limit)
- Entered via "Learn the tool" on the landing page → Skill Select screen
- Explain Panel: clicking any device node, metric card, alert row, or packet row opens a plain-language explanation of what that element represents and what it indicates about network health
- Explain Panel has entries for every device type (6), every metric key (20+), every alert level (3), and every protocol (6), plus a fallback for unknown keys
- Hint system: all hints are available, revealed one at a time on request
- Diagnosis: the Diagnosis Modal is available; after submission the full explanation is shown automatically; progress is recorded anonymously to localStorage (key: `nw_teach_{lessonId}`, no student identity)
- Self-Check button (🎯) replaces the Diagnose button in the lesson bar — see Skill-based learning below

**Quiz Mode** (student login, attempt-gated, server-side result recording)
- Entered via "Take a scenario" on the landing page → Lesson Select screen → login
- Explain Panel is fully suppressed (function-level guard + CSS quiz-mode class on `<body>`)
- Hint system: only the first hint is available; "Next Hint" is disabled after the first reveal
- Diagnosis: POST to `/api/results` on submission; student name + NPM shown in result; auto-retry once on failure; inline error if retry also fails
- Attempt gate: `POST /api/attempts` before each simulation load; blocked-attempt screen if limit reached (shows prior correct result if one exists)
- No plaintext password anywhere in frontend source

### Skill-Based Learning (Teach Mode)
Four panel-reading Skills, each with:
- A reference card explaining how to read that panel (topology colour coding, chart windows, alert severity levels, packet flagging)
- A cross-reference to which lessons demonstrate that skill most clearly ("Comes up in: …")
- A three-question **Self-Check** (ungraded, no backend, no attempt limit):
  - **Recall** — multiple-choice definition question (e.g. "what does a red node mean")
  - **Reading** — click-to-answer on the live panel (e.g. "click the ISP↔GW-1 link")
  - **Synthesis** — multiple-choice interpretation of two signals together (e.g. "amber node + amber link — what does the combination tell you")
- A "✓ COMPLETE" badge on the skill card after finishing all three questions (in-memory, session-only)
- Each skill launches the simulation whose incident best illustrates that skill's target panel

### Lesson Data Model
`src/lessons.js` exports a full structured content model:
- `LESSONS` — 6 entries, each with: topology id, incident id, difficulty, description, objective, MCQ options + correct answer, hints array, full explanation, and a `steps` array (concept → watchFor → simulation → quiz)
- `COURSES` — 3 grouped learning paths: Edge & Gateway Attacks, Server-Tier Degradation, Specialised Infrastructure
- `SKILLS` — 4 panel-reading reference cards, each with `selfCheck` questions and `lessonRefs`
- `TOPOLOGIES` — 3 topology templates (nodes + links with positions)
- `INCIDENTS` — 6 scripted stage sequences (timed targets, link changes, alerts, log lines)
- `getSimulationConfig(lesson)` — accessor that resolves a lesson's simulation step to the full topology + incident objects the engine expects

### Authentication & Backend
- Student login: NPM (digits only, 1–20) + password → `POST /api/auth/login` → JWT in memory (never localStorage/sessionStorage)
- Instructor login: separate credential → instructor JWT → unlocks Admin Reset
- Attempt gating: counter stored per (npm, lessonId) pair; `ATTEMPT_LIMIT = 3` server-side constant
- Result recording: append-only `Result_Records` table; server-generated timestamp; no client-side modification possible
- Admin Reset: instructor-JWT-authenticated `POST /api/admin/reset` resets attempt counter without touching result records
- All token signing and credential verification happen exclusively on the backend

### Sandbox & Developer Controls
- Manual override slider: forces focus-device load to any value 0–100%
- Test alert injection: manually fire CRITICAL / WARNING / INFO alerts for UI testing
- Notes area: freeform text pad (in-memory, session only)

## Key Data Flows

### Teach Mode (no network after page load)
```
Landing "Learn the tool"
  → Skill Select screen (renderSkillSelect fills #skill-grid from SKILLS)
  → skill card click
      → setStudentSession(null, null, null, 'teach')
      → launchSimulation(lessonId)
          → createInitialState(lesson) → simState
          → tick loop (setInterval 1 s) → renderAll()
          → attachExplainListeners() [idempotent, teach-only]
          → btn-diagnose swapped to "🎯 Self-Check"
  → student explores, clicks elements → showExplainPanel(key) → Explain Panel
  → student clicks "🎯 Self-Check"
      → startSelfCheck(skill, { onComplete })
          → modal-selfcheck: recall MCQ → reading click-to-answer → synthesis MCQ
          → onComplete: completedSkills.add(skillId) → renderSkillSelect() [badge]
  → student clicks "← Back"
      → exitSimulation() → teardownSelfCheck() → showSkillSelectScreen()
```

### Quiz Mode (requires backend)
```
Landing "Take a scenario"
  → Lesson Select screen (renderLessonSelect fills #lesson-grid from LESSONS)
  → lesson card click → pendingLessonId stored → modal-login opens
  → student submits login
      → validateLoginForm() [client-side, pure]
      → api.login(npm, password) → POST /api/auth/login
      → setStudentSession(token, name, npm, 'quiz')
      → api.startAttempt(lessonId) → POST /api/attempts
          → allowed:true  → launchSimulation(lessonId)
          →               → btn-diagnose stays "🩺 Diagnose"
          → allowed:false → blocked screen + GET /api/results (show prior correct)
  → tick loop runs
  → student clicks "🩺 Diagnose" → Diagnosis Modal
      → submitDiagnosis()
          → api.recordResult(lessonId, outcome) → POST /api/results [auto-retry once]
          → show name + NPM in result
  → student clicks "← Back"
      → exitSimulation() → showLessonSelectScreen()
```

## API Endpoints

| Method | Path | Auth | Description |
|---|---|---|---|
| POST | `/api/auth/login` | none | Student or instructor login; returns JWT + name |
| POST | `/api/attempts` | student JWT | Check + increment attempt counter; returns `{ allowed }` |
| POST | `/api/results` | student JWT | Record diagnosis outcome (append-only) |
| GET | `/api/results` | student JWT | Get all results for a student + lesson |
| GET | `/api/results/all` | instructor JWT | Get all results across all students and lessons |
| POST | `/api/admin/reset` | instructor JWT | Reset attempt counter for a (npm, lessonId) pair |

## Database Schema

```sql
Student_Accounts    (npm PK, name, password_hash, created_at)
Instructor_Accounts (username PK, password_hash, created_at)
Attempt_Counters    (npm + lesson_id PK, count, last_attempt_at)
Result_Records      (id SERIAL PK, npm, lesson_id, outcome CHECK('correct','incorrect'),
                     recorded_at)   -- append-only, never updated or deleted
```
